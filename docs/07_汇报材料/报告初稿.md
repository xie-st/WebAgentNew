# Web Agent 的并行执行与容错调度

**队名：勇闯天涯**

**队员：陈思旭、寇之洲、谢树韬**

**代码仓库：[xie-st/WebAgentNew](https://github.com/xie-st/WebAgentNew)**

## 1. 问题与基础工具

本项目面向网页任务中的并行执行、结果确认、容错恢复和频率控制。在比赛指定的 Qwen3.6-35B-A3B 模型下，我们希望让 Agent 根据页面反馈持续推进任务，在操作失败、结果不明或需要人工介入时保留有效进度，并利用独立页面之间的并行空间缩短执行时间。

开发工具采用 Codex、WorkBuddy 和 DeepSeek Harness（DSH）。它们提供文件读写、代码检索、命令执行、测试及任务派发等通用能力，使方案能够经由明确的实施文档交给多个开发智能体执行。Codex 侧使用 GPT-6.1 Sol，推理强度为 Medium；WorkBuddy 使用 GLM-5.3-flash；DSH 通过硅基流动 API 调用 DeepSeek v4 flash 1013。上述开发工具提供通用工程能力，不包括本项目所需的 Web Agent 具体知识；赛题理解、论文方法选择和路线规划由团队完成。

运行系统以 EffGen 为基础框架，复用其观察—思考—工具调用—反馈循环，以及轨迹、预算和上下文压缩机制。[1] Playwright 提供真实浏览器的页面操作、观察获取与截图能力，官方 SDK 提供评测平台的观察、动作和模型接口。我们围绕这些入口补充统一网页工具、环境适配和任务状态管理。开发模型用于构建工程，提交的 Web Agent 使用比赛指定模型执行网页任务。

## 2. 从人工规划到工程实现

工程过程由人工确定问题和优化方向开始。团队先阅读赛题与接口要求，围绕观察效率、长期任务状态、结果核验、失败恢复和并发调度查询论文，再形成 RoadMap，确定优先级与三阶段路线。

随后由 Codex 将 RoadMap 翻译成各阶段的详细方案、DSH 实施说明、验收要求和测试任务。实施说明写明输入输出、模块职责、文件归属及前置依赖，使开发智能体能够按文档实现，并与其他模块衔接。方案经人工审定后，由 WorkBuddy 将任务交给 DSH，完成代码实现与离线验证；主线程负责集成、真实模型与浏览器验证，以及官方平台接入。每批结果反馈后，再确定后续工作。

开发中的并行按现有模块边界安排。输入与观察适配、状态与恢复支持、本地任务与判定可独立开发；公共驱动、官方入口、配置和命令行由一个集成负责人统一合入。并行写任务各用一份包含当前源码的独立副本，测试前确认导入该副本的代码，交回后按文件归属审查并顺序集成。强依赖部分先固定接口，再接入调用方；真实模型和官方评测顺序运行。

这一安排在第二阶段用于输入适配、状态恢复和本地判定三线开发；之后将恢复接线、上下文与经验加载、并行调度骨架分开准备。调度的全局暂停功能仍依赖恢复与接管接口，待接口合入后集成验证。

## 3. 第一阶段：双环境跑通

第一阶段解决同一个 Agent 如何在官方平台与真实浏览器中连续执行。我们固定 EffGen 源码与官方 SDK 版本，建立模型适配器、统一观察与动作协议、会话管理和证据存储，再分别连接两套环境。

关键改动是在 EffGen 原有循环中加入可暂停的生成器接口。需要执行网页动作时，循环交出动作并暂停；环境执行后，将新观察送回同一生成器继续。官方端由每次 `step()` 推进，返回一个动作；真实端由本地浏览器执行并回传观察。读取任务状态、保存证据等内部工具在本地完成。

两端共用点击、输入、按键、滚动、导航等网页工具。每个动作绑定当前页面、观察版本和有效元素编号，页面更新或人工接管后重新生成定位信息。日志关联任务、观察、动作、反馈、模型调用和截图，为后续核验与恢复保留依据。

真实浏览器接入比较了 Playwright 与 browser-use 的浏览器层，选择 Playwright 作为默认后端。阶段交付覆盖真实模型调用、本地页面任务、公开网页访问、人工暂停继续，以及官方任务的基本运行链路。

## 4. 第二阶段：基础能力与测试环境

### 4.1 任务状态、结果确认与恢复

第二阶段的建设方案围绕长任务建立状态与证据之间的联系。任务账本保存目标、已知事实、缺失信息、待确认操作和证据引用；EffGen 继续负责规划与行动，程序负责状态转换、版本检查和持久化。模型只表达业务目标与判断，版本号、分支和证据归属由程序绑定。

结果确认放在保存、提交、子目标结束和任务结束等关键节点。可以直接判断的条件由程序检查，需要语义判断的条件交给比赛模型。核验未通过时，将缺口反馈给同一执行循环继续纠正。恢复时依据证据撤回受影响的完成判断，保留其他已确认进度；有副作用的操作超时后，先核实页面结果再决定是否重试。

人工接管覆盖登录、验证码、二次验证和主动暂停。系统先停止新动作并处理在途操作，再交出浏览器；用户确认继续后重新观察页面，使旧动作提案和元素编号失效，再根据新状态推进。

测试环境分为本地可重置网站、官方论坛与电商调测、公开真实网站三层。本地任务用于复现状态变化、执行故障和接管流程；官方平台检查完整任务结果；真实网站检查实际交互与多页面协作。各能力通过独立开关接入实际运行入口。

### 4.2 优化方向与论文来源

团队从任务失败方式出发选择候选方法，并将论文思路转成适合固定模型和浏览器接口的工程设计。

| 方向 | 论文依据 | 本项目的采用或候选方式 |
| --- | --- | --- |
| 当前任务状态与停滞诊断 | PoS / BeliefState [2] | 区分已知事实、未解决要求与待确认结果，以目标进展和证据变化判断停滞。 |
| 结果核验与反馈纠错 | WALT [3]、Reflexion [4] | 为子目标设置可观察的完成条件，将核验反馈送回执行循环；短反思作为候选，记录具体修正办法。 |
| 同轮摘要与通用经验 | M² [5] | 候选方案为行动同轮生成短摘要；经验先提供人工批准文本的加载入口，默认空库。 |
| 按子目标折叠历史 | AgentProg [6] | 候选方案为折叠已完成过程，将后续仍需使用的对象值与证据保存在账本。 |
| 观察表示与历史差分 | Read More, Think More [7] | 保留当前观察，候选方案用差分表达旧观察，减少历史重复内容。 |
| 页面候选筛选 | Prune4Web [8] | 候选方案由模型给出关键词和权重，固定程序遍历评分，保留候选与当前可操作元素的对应。 |
| 多页面依赖调度 | Flash-Searcher [9] | 借鉴依赖图组织独立任务，以页面归属、共享状态约束和统一限流安排真实浏览器分支。 |
| 截图与行动效率 | UI-TARS [10]、WebClipper [11] | 截图先用于页面留证；截图参与决策、轨迹依赖分析和通用动作组合列为后续候选。 |

实施时优先完成基础状态、最小核验和同循环纠错，再接恢复与人工接管。上下文部分先保护当前观察和必要账本，提供独立开关与批准文本加载；摘要、差分、折叠、筛选及动作组合保留为待比较的方法。

### 4.3 运行时的并发处理

真实端首版将独立只读任务分配给不同 Tab，每个分支拥有独立循环、会话和观察；共享写操作串行执行。每个 Tab 同时最多执行一个动作，一个生成器由单一所有者推进。浏览器操作通过统一所有者调度，不将同步页面对象交给多个线程。

并行从两个分支起步，容量可配置；模型调用并发初始为一，先重叠不同页面的等待。所有分支共用根任务预算、站点访问节奏与退避状态，防止分支增加后总访问频率成倍上升。共享账本更新由协调器串行提交，过期版本需重新核对。人工接管触发全任务暂停，恢复前统一刷新相关页面状态。

官方端按单任务、单动作的接口串行执行，多页面调度在真实浏览器端接入。
