# 状态、检验与恢复核查

日期：2026-10-30。归属：RoadMap 实施前的论文依据。本文记录研究判断和方案候选，不是已批准的实施方案。

## 综合判断

状态维护回答“现在知道什么、还有什么未完成”；结果检验回答“哪些证据足以确认要求已满足”；失败恢复回答“当前策略哪里受阻、接下来改变什么”；反思回答“这次反馈能转成什么可复用教训”。四者应共享事实与证据，但不能用同一段摘要代替。

PoS 提供状态更新、一致性核对和停滞诊断的组织方式；WALT 提醒完成声明需要复核，也给出了工具契约与离线验证的方法；Reflexion 将反馈转成后续尝试的行动指导。RoadMap 要求的“定位最早因果错误并从断点续做”，仍需本项目建立动作、证据和子目标的依赖关系，不能仅靠引用 Reflexion 就认为已经具备。

## PoS／BeliefState

作者针对的问题是：即使历史保存得完整，Agent 仍可能把过时信息、当前事实和推断混在一起；即使状态内部自洽，行动也可能一直不推进目标。因此将当前世界估计与目标缺口分开维护，并在更新后检查一致性与进展。

世界状态采用实体、状态、关系，附来源、置信度和可用证据；目标缺口区分“还缺信息”和“还缺行动结果”。当前活动缺口让行动保持焦点，但其余任务要求继续保留。观察返回后先生成候选更新，经过 Sentinel 检查和 Agent 修订再提交。

其停滞判断结合未解决要求的持续、无进展与状态重现，而非仅数重复动作。恢复按“静止、循环、偏离目标”和受阻缺口组合约束：寻找新证据与真正改变任务状态是两类不同的恢复目标。附录 B 还说明：若不能归入三类则使用通用恢复；不能强行给每次失败套一个分类。

本项目适配判断：账本应区分已观察事实、暂定解释、待补信息与待完成要求；状态修订需要指向观察和动作记录。页面变化本身不代表业务进展，连续相同动作也不必然代表停滞。停滞检测应围绕当前子目标及其证据判断。

实验支撑评分：8/10，支持持续维护一致性与进展的核心故事。

证据位置：[本地材料](论文/09_PoS-BeliefState.md) §2–3、§4.1–4.4、附录 B、C.3–C.4、D.1–D.4。已核对更新顺序、恢复约束、预算口径与实现参数。原实现涉及任务 Agent、belief 更新与 Sentinel 的计算开销；其成本表把各组件分别计算，不能只将任务 Agent 输入减少视为总成本下降。原文逐步更新、局部审计和周期性全局审计等参数属于待比较机制，不直接设为比赛默认配置。

一手页面核对：[arXiv:2610.01415v1](https://arxiv.org/html/2610.01415v1)，版本为2026-10-01；本轮不作作者连续研究的独立评价。

## WALT

作者希望将网站已经提供的功能转成有契约、可复用的工具，减少每次都从底层操作重新推理。主要方法是探索、示范、生成与验证工具，并通过结构化输入、稳定定位与失败反馈改进实现。它不是一篇以“寻找最早因果错误、局部回滚”为主线的论文。

对 RoadMap 的直接启发是：工具调用、Agent 自报完成与真正满足任务要求要分开。WALT 的外部验证复核执行者的完成判断，工具离线验证则检查一个可复用实现能否在测试输入上工作；二者不是同一种验收。

本项目适配判断：为子目标写出可观察的完成条件，记录确认依据；最终逐项检查任务要求。可以把核验作为 EffGen 可调用的能力，在合适节点执行。核验策略应单独开关与计费，不预先规定每步额外调用一个模型。规划者与核验者使用同一比赛模型时，角色分离也不能自动等同于客观真值。

实验支撑评分：8/10，支持功能工具化与完成复核的核心故事。

证据位置：[本地材料](论文/05_WALT.md) §2–3（工具构建）、§4.3（实现）、§4.5／表2（组件比较）、附录 A.1–A.2（自报完成分析、工具算法与实现）。已读取正文、相关工作及上述附录文本；图示或未展开的提示词不作完整转录声明。一手页面核对：[arXiv:2510.01524v1](https://arxiv.org/html/2510.01524v1)。

原论文还包含 URL 路由逆向与操作序列提升；本项目不把这些做法默认搬入比赛方案。所有网页动作、观察获取和复用工具均须服从官方协议及真实浏览器操作要求，按最新 SDK 的明确能力实现。

## Reflexion

作者解决的是反馈稀疏、模型又不能每次都重新训练的问题：把失败信号、轨迹和已有经验转成具体的语言指导，供下一次尝试使用。Actor、Evaluator、Self-Reflection 是职责划分，反馈可以来自环境、程序规则或模型；并非要求使用三个不同规格的模型。

关键在于反馈与下一次行动之间有一段具体的修正指导，而不是泛泛自我批评。原文 ALFWorld 流程在反思后重置环境并开始新 trial，反思记忆有容量限制。因此，本项目只借鉴有反馈依据的教训提炼；“当前任务内保留已完成部分、只重做受影响部分”属于另外需要实现和验证的恢复机制。

实验支撑评分：8/10，支持反馈驱动的语言经验帮助后续尝试的核心故事。

证据位置：[本地材料](论文/06_Reflexion.md) §2–4、§5–8、附录 A、B 的决策示例与 B.1、C.1–C.5。已核对环境重置、经验窗口、反馈来源与消融；附录 D 的问答完整示例未逐条阅读，当前判断不依赖其全部示例。论文的 WebShop 结果也已读入核查依据，未将该论文视为电商任务普遍有效的证明。

一手页面核对：[arXiv:2303.11366](https://arxiv.org/abs/2303.11366)。页面当前为 v4（2023-10-10）；本地转录未固定版本，方法判断以已读本地文本为依据，不声称已逐字核对其与 v4 的差异。

## 对阶段方案的约束候选

第一阶段在跑通循环的同时，必须能关联任务、观察、动作和反馈，区分“已发出”和“有证据确认”。报错、超时及结果不明都要返回给 Agent，并保留可核查记录。这是基础可观测性，不在本阶段预装完整的多角色审计系统。

第二阶段围绕已有账本加入完成条件、证据引用、当前受阻要求与恢复入口。拟采用的职责顺序是：读取新观察，核对上一动作影响，修订相关状态，再由 EffGen 决定继续、核验、恢复或完成。登录接管结束后重新观察，也走同一更新过程；恢复时只失效与当前冲突有关的状态，不清空全部已验证进度。

对于有业务副作用的动作，超时或反馈缺失记为结果不明，先核实真实页面再决定重试。恢复所依赖的候选记录至少包括：对象标识、子目标、前置要求、动作与观察引用、预期结果、已观察结果和确认状态。确切 schema 与转换规则留待阶段详细方案定稿。

第三阶段分别比较检查时机、停滞判断、恢复约束和反思提示。需要计入所有内部模型调用与网页操作成本；只有预算、样本与评价口径一致时才比较机制。实验批次仍逐批提交用户审批。
