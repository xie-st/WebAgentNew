## 接线实现

### 1. 状态工具注册

`create_stateful_driver(session, model, store, branch="root")` 内部：

```python
tools = list(extra_tools)
tools.extend(build_state_tools(StateToolRuntime(store, branch=branch)))
return create_driver(session, model, ..., extra_tools=tools)
```

没有把状态工具放进 `TOOL_SPECS`，也没有改 `build_harness_tools` 的封闭分派。L01 证据中模型首个动作是 `state_read`，说明工具经 EffGen 既有工具路径真实执行；`test_l01_end_to_end...` 同时断言 `STATE_TOOL_NAMES <= set(driver.agent.tools)`。

偏离说明：D3 的 Goal／Plan 由测试侧用公开 case 视图（任务原文、公开条件、`completion.criteria`）通过 `PlanUpdate` 直接建立，用于验证账本接线；没有让假模型调用 `plan_update` 生成计划。`plan_update` 工具的模型路径已由 D2 测试覆盖，D3 不重复宣称模型自主规划能力。

### 2. 副作用接线

`EffGenLoopDriver.take_action(before_dispatch=...)` 在 `Session.consume` 之前调用回调。`StatefulLoopRunner` 用这个槽：

1. `EffectPolicy.classify(action, observation)`；只对显式规则命中的写动作返回 `EffectIntent`；
2. `StateStore.prepare_effect(action_id, target, object_id, goal_id, branch, observation_id, note)`；
3. 正常返回后才 `take_action` 消费并交给 backend；保存失败时回调抛错，runner 记录错误、取消任务，backend 不执行；
4. backend 返回反馈后 `confirm_effect`：`observed→confirmed`、`error→failed`、`unknown→unknown`；
5. 若 `prepare_effect` 成功但消费阶段失败，确认 `failed` 并注明“dispatch aborted”；若 backend 执行抛异常，pending 保留为未知，不以猜测确认。

显式分类表（`DEFAULT_EFFECT_RULES`，顺序匹配，先具体后泛化）：

| 类别 | 触发 |
| --- | --- |
| `draft_save` | 点击名含 `save draft` |
| `draft_clear` | 点击名含 `cancel draft`／`discard draft` |
| `comment` | 点击名含 `send comment`／`post comment`／`submit comment`／`publish comment` |
| `purchase` | 点击名含 `add to cart`／`checkout`／`place order`／`buy now`／`purchase` |
| `submit` | 点击名含 `submit`／`save changes`／`save`／`send`／`publish`／`confirm`／`delete`；以及 `web_type` 且 `submit=true` |
| 非副作用 | 链接导航、详情打开、普通输入、滚动、`web_goto`、无 submit 的输入 |

偏离与解释：任务示例写“保存／提交／评论类”，本批把 `Cancel draft` 也归为 `draft_clear`。理由是它确实修改服务端保存的草稿（清空），而 L01 按要求不能点 `Save draft`；若不分类，L01 的正常链路将没有可验证的 pending effect。分类仍是显式的、按动作语义声明的，不是“所有动作都写 pending”。L01 证据为 6 个已执行动作、1 个 pending effect。

`web_press` 的 Enter 没有自动归类：搜索框回车通常是导航，表单回车才可能是提交，仅凭按键无法可靠区分；需要由计划节点或后续工具规格显式声明。计划节点声明副作用本批未实现，只实现工具层声明表。

### 3. 事件字段

`events.py` 的每条事件现在都有四个字段的显式默认 null；`EventLogger.set_state_context(provider, goal_id=...)` 在每次 emit 时读取当前 store revision／plan_version／branch，合并非空值。旧 `EventLogger` 不设 provider 时行为与之前一致，只多出四个 null 字段；`REQUIRED_FIELDS` 未改。

L01 的 `Cancel draft`（action id `act_887...`）证据：

| 事件 | state_revision | goal_id | branch_id | plan_version | result |
| --- | --- | --- | --- | --- | --- |
| `proposed` | 2 | g1 | root | 1 | null |
| `dispatched` | 4（prepare 后） | g1 | root | 1 | null |
| `feedback` | 5（confirm 后） | g1 | root | 1 | observed |

proposed 与 dispatched 之间的 revision 差包含“上一条观察写 Fact”和“本动作 prepare effect”两次提交，不是单一 prepare；测试只断言 proposed < prepared.created，dispatched == created，feedback == updated。

### 4. 观察事实、证据与判分回写

`StatefulLoopRunner` 每次收到观察后调用调用方提供的 `observation_recorder`；D3 夹具识别 `/product/<id>`，返回 `ObservedObject(object_id, fields)`。runner：

- 从该观察已保存的 `screenshot` Artifact 生成 `EvidenceRef`（relative reference、SHA-256、byte_size、observation_id、action_id、branch/run 归属）；
- `record_observed_object` 写 `Fact(field="page_observed", kind=observed, evidence=(ref,))`，同一对象重复观察只增加 Fact revision 与证据，不重复计对象；
- 若 goal 的 `object_scope` 含该对象，追加 `completed_object_ids`（元组集合语义），Goal 保持 `running`／`pending`，绝不在这里 verified。

judge 证据不是另造一份：测试从账本 Fact 的 `EvidenceRef` 生成 `EvidenceRecord`（绝对路径指向同一文件，带同一 sha256），交给 D1 的 `judge`。judge 通过后，再取账本 Fact 的同一组 `EvidenceRef` 调 `StateStore.verify_goal`；没有证据文件或 judge 不通过时不调用该入口。

判分前快照（`runtime/phase2_d3/state_before_judge.json`）显示：revision 7、plan_version 1、Goal `running`、verified 列表空、completion `incomplete`、Fact revision 4、object_progress `1/1`、`goals_verified=0`。判分后（`state_after.json`）revision 8、Goal `verified`、completion `complete`。这对应 D03 的“observed 不等于成功、verified 需证据”。

judge 失败变体（seed 303，故意不给 judge 证据）在 `test_failed_judge_does_not_write_verified`：judge 的 `screenshot` 检查失败、`passed=false`；账本仍有 observed Fact 与证据，但 Goal 保持 `running`、verified 为空、completion 仍 `incomplete`，快照重载一致。
